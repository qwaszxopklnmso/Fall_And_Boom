# Fall_And_Boom

Windows 桌面小玩具：图片从屏幕顶端掉落，落到窗口顶边会停住并跟着窗口移动，
被快速拖动的窗口"创飞"，存活 5 秒后炸成碎片，爆炸还会把附近的图片一起炸飞。
被以特别快的速度撞击时，引信会缩短 2.5 秒。

> 详见文末的「AI 生成声明」与 [LICENSE](LICENSE)。

## 特性

- Win32 + GDI+ 单窗口合成，整屏 layered window 一次提交
- 图片格式：`png` / `jpg` / `jpeg` / `bmp` / `gif` / `webp` / `tif` / `ico`
  - 优先用 GDI+ 解码；遇到 WebP、JPEG XL 等它不认识的格式自动回退到 WIC
  - 支持多帧 GIF 动画
- 把其它程序的窗口顶边当作平台；**全屏 / 无边框全屏窗口会被忽略**
- **被其它窗口遮住的那段顶边不会被当成平台**，不会出现"悬空停住"
- 停住的图片会跟随窗口做**水平和垂直**移动（窗口往上拖也会被顶上去），
  而且**拖动多快都跟得上**（不再有 250 px/s 的速度上限）
- 被撞飞的图片会与**窗口侧面**正常碰撞推挤，不会穿模
- 把窗口往**上**拖时，压在它顶边上的图片会被一起顶上去，不会穿过窗口
- 顶边上面**放得下才站得住**：48px 的图片要顶边在 y ≥ 48，12px 的碎片 y ≥ 12 就够。
  顶边贴着屏幕上沿的窗口（含最大化、贴顶）就穿过去，不会被硬塞到屏幕顶端卡住
- **爆炸产生的碎片也会落在窗口顶边上**（和图片用同一套落点判定）
- **开始菜单 / 搜索 / 通知中心这类 shell 浮层也能碰撞**（见下方「z-band 窗口」）
- 顶边太低（贴着屏幕顶端，例如右侧贴满全高的通知中心）的窗口站不上去，
  但它**落在工作区里的那条侧边仍然是墙**，弹飞的图片会撞在上面
- 爆炸产生冲击波，把半径内的其它图片一起炸飞（被炸飞不变浅）
- 爆炸前 3 秒开始闪烁，0.6 秒一个周期
- **按 `.` 在鼠标位置立刻生成一张随机图片**（不用等自动生成）
- 光标完全穿透，不抢焦点

## z-band 窗口（为什么开始菜单要单独处理）

Win11 的开始菜单、搜索、通知中心这类 shell 浮层是用 `CreateWindowInBand` 建在
**比默认 z-band 更高的 band** 上的。它们是货真价实的顶层窗口 ——
`WS_POPUP | WS_VISIBLE`、父窗口是桌面、没被 DWM cloaked、`GetWindowRect` 也正常 ——
但下面这些 API **一个都枚举不到它们**（实测确认）：

`EnumWindows` / `EnumChildWindows(GetDesktopWindow())` / `FindWindow` /
`GetWindow(GW_CHILD)` 链 / `EnumThreadWindows`

唯一能拿到的是 `GetForegroundWindow()`。所以 `ScanWindows()` 会先问一次前台窗口：
如果它**不在** `EnumWindows` 的结果里，就说明它是 band 窗口，于是把它插到
`g_windowList` 的最前面（它的 Z 序本来就在所有窗口之上）。这样它既能当平台，
又能作为遮挡源，让被它压住的其它窗口顶边正确地失去停靠点。

代价：一次扫描多一次 `EnumWindows` 探测（命中前台窗口就提前返回，通常几十次迭代）。
另外 band 窗口同一时刻只可能有前台那一个，但 shell 浮层本来也是互斥弹出的。

## 碰撞解算（为什么"上推"要单独处理）

### 1. 落点判定：`CrossesTopEdge()`

窗口矩形是每 `WINDOW_SCAN_SEC`（默认 0.08 秒）采样一次的，所以快速拖动时
**一帧能跳几十甚至上百像素**。这会让"最小穿透深度"这套判定选错轴：

- 窗口**往下**压或左右推时，图片相对窗口是"迎上去"的，最小穿透轴天然是对的轴；
- 窗口**往上**冲时，图片相对窗口在往下走，于是"从窗口底边穿出去"会先变成最小穿透轴
  —— 图片被从窗口下沿挤出来，看起来就是窗口从它身上穿了过去。

更麻烦的是，如果窗口一帧直接跳过了图片，两者**根本不再相交**，连重叠判定都不成立。

所以落点判定统一走 `CrossesTopEdge()`，它是两条判据取或：

**（a）图片掉下来 —— `SweptDownPastTop()`**：参照边取
`max(上一拍的顶边, 这一拍的顶边)`。

- 窗口静止 / 下移 → 参照边 == 当前顶边，判据和以前完全一样，行为不变；
- 窗口上移 → 参照边 == 上一拍的顶边，"原本在顶边之上、这一拍被吞进来"
  就能判出来，图片会被顶到新的顶边上。

**（b）窗口顶边升上来 —— `RisingTopLifts()`**：光有 (a) 还不够。

(a) 的前提是"图片底边上一拍还在顶边**之上**"。可图片经常是**停在屏幕底部
（或别的平台上）不动**的，窗口顶边从它下面升上来时，第一拍就可能已经越过它的底边
（窗口上一拍还在工作区外面 / 刚进列表，没有上一拍记录），之后 `prevBottom` 永远
大于参照顶边 —— 判据一直不成立，顶边直接从图片身上升过去。
表现出来就是**"接不住也推不动"：顶边扫过图片，图片纹丝不动**。

所以再按"扫掠"本身判一次：顶边这一拍扫过的竖直线段 `[这一拍顶边, 上一拍顶边]`
如果与图片身体 `[底边 - 高度, 底边]` **相交**，并且图片底边现在还在新顶边之下，
就把图片抬到新顶边上（并记下 `restingOn`，之后由第 4 节的跟随逻辑接管）。

- 顶边本来就远在图片上方的（图片整个在窗口肚子里）**不算** —— 那是一次瞬移，
  这正是以前"图片突然被吸到窗口顶上"的成因。

替换成一句话：**图片底边越过顶边**（图片掉上去）和**顶边越过图片身体**
（窗口顶边升上来），两种穿越都要认。

多个平台同时命中时由 `FindLandingTop()` 取**顶边最高**的那一个：正常下落时先碰到
的就是最高的那块；被上升窗口吞进来时，这也是唯一不留下穿模的解（落到更低的那块上
会和已经升上来的窗口重叠，下一帧再被抢一次，来回抽搐）。

图片、被弹飞的图片、爆炸碎片三条路径用的都是这套判定，所以碎片也会停在窗口顶边上，
而且会跟着窗口上下走。

### 2. 飞行的图片：先看"从哪进来"，再看"离哪条边近"

被弹飞的图片（抛物线状态）走的是 `CollideWithWindows()`，它按**最小穿透深度**选轴。
这套规则有个坑：它只看"离哪条边近"，不看图片是从哪进来的。

于是图片贴着窗口左/右边缘时 `pLeft`/`pRight` 比 `pTop` 小，就被甩到窗口侧面；
贴着窗口底边时 `pBottom` 最小，被甩到窗口下方 —— 视觉上就是
**"用窗口上缘推图片，图片瞬移到窗口下方/侧方，直接穿过窗口"**。
这跟拖动快慢完全无关，慢速一样错。

两道修正：

1. **从上方越过顶边进来的，一律顶回顶边上面**（`CrossesTopEdge()`），
   根本不给最小穿透深度机会。顶边被更高 Z 序窗口压住时不这么解。
2. **左 / 右 / 下三条边只在"这一帧刚穿过去"时才作数**，也就是穿透深度不超过
   一个身位（`pLeft/pRight <= 宽度`、`pBottom <= 高度`）。深陷窗口肚子里的图片
   干脆不解析，让它自己按物理落出去 —— 总比瞬移到另一条边上强。
3. **底边还要看相对运动方向**：只有图片相对窗口**往上走**（从下面撞上来）才按
   底边解算。否则一个往下穿过窗口的图片会在退出窗口底边的瞬间被"啪"地按到
   `wr.bottom` 上，无端跳一下。

### 3. 顶边上面放不下就别硬塞（`TopEdgeFits()`）

"这条顶边能不能**接住**一张图片"是按**图片自己的高度**算的：`窗口顶边 y >= 精灵高度`。

- 48px 的图片需要顶边在 y ≥ 48 以上；
- 12px 的爆炸碎片只要顶边在 y ≥ 12 以上，所以碎片能停在图片停不了的矮窗口上。

顶边在屏幕上方（`top < 高度`）的窗口接不住，就**老老实实让图片穿过去**——
全屏、最大化窗口（顶边在 -7）也因此自动出局，不必再单独判。

> 曾经试过放宽成"顶边贴着屏幕上沿也算平台"，再把图片的 `y` 钳到 0。
> 结果是一场灾难：被拖到屏幕上沿的窗口（以及拖动时系统临时冒出来的全宽浮层）
> 全变成 y=0 的架子，**新生成的图片一出来就卡在屏幕最上方不下落**。
> 所以"接住"这条不能放宽：放不下就是放不下。

### 4. 已经在顶边上的图片：跟着窗口走，不设速度上限

"接住"严格，但**已经停在顶边上的图片**是另一套逻辑，它必须一直跟着窗口：

- **不要求 `TopEdgeFits`**。窗口被往上拖到顶边上面放不下时，图片压在 `y = 0`
  继续跟着走。放掉它才是错的 —— 用户看到的是"图片莫名其妙从窗口顶边上掉下去"。
- **水平跟随不设"游戏性"上限**。原来卡在 `FOLLOW_MAX_VX = 250 px/s`，
  而拖动窗口轻松就超过它，于是窗口直接从图片脚下被抽走 ——
  "图片跟不上 / 滑出去 / 然后掉下去"。图片本来就压在窗口顶边上，窗口一动它当然
  要跟着走。现在只留一个荒谬值上限（`FOLLOW_SANITY_VX`）挡窗口矩形抖动。
- **垂直位置在扫描点对齐、帧间按窗速外推**。窗口矩形每 0.08s 才采样一次，
  只写 `y = 顶边 - 高度` 的话图片每 0.08s 才动一下，看起来一顿一顿地"跟不上"。
  所以扫描那一帧精确对齐（`g_scanAccum == 0`），之后按 `顶边速度 × 已过去时间`
  平滑外推，下一次扫描再对齐回来。水平方向顶边上没有参照点，只能按窗速积分。

## 图片

把图片放进 exe 同目录的 `images\` 文件夹（按文件名排序，最多取前 10 个）。

每张图片统一存活 **5 秒**，然后爆炸成 4×4 的碎片。
被以特别快的速度撞击（相对速度 ≥ 800 像素/秒）会**提前 2.5 秒**爆炸。

爆炸前 3 秒开始闪烁。所以满血时只在生命最后 3 秒闪；
而挨过一次重击后剩余寿命变成 2.5 秒，会立刻开始闪。

> WebP 依赖系统安装的解码器（Win10/11 通常自带）。
> 若某张图片解不了，程序不会崩溃，只会在全部图片都失败时弹窗列出文件名。

## 手动生成（按 `.`）

主键盘区的 `.` 每按一次就在鼠标当前位置生成一张随机图片（以光标为中心，
会夹进工作区，不会生成到屏幕外）。长按的自动重复会被 250ms 去抖挡掉。

自动生成和手动生成可以单独关掉，两个开关都在 `main.cpp` 顶部的「生成方式开关」：

| `AUTO_SPAWN_ENABLED` | `MANUAL_SPAWN_ENABLED` | 效果 |
|---|---|---|
| `true` | `true` | 默认：自动随机下落，随时可以按 `.` 补一张 |
| `false` | `true` | 屏幕一直干干净净，**只有按 `.` 才会出现图片** |
| `true` | `false` | 只能等自动随机下落，连键盘钩子都不会装 |
| `false` | `false` | 什么都不会生成（退出热键仍然有效） |

关掉 `MANUAL_SPAWN_ENABLED` 时连 `WH_KEYBOARD_LL` 钩子都不装，
不会白白往系统里挂一个全局键盘钩子。

实现上不能用 `RegisterHotKey`：那会把这个键从**所有程序**手里抢走，
打字、输入小数点就全废了。也不能靠 `WM_KEYDOWN` —— overlay 窗口带
`WS_EX_NOACTIVATE | WS_EX_TRANSPARENT`，永远拿不到焦点。
所以这里装的是 `WH_KEYBOARD_LL` 低级键盘钩子：全局看得见，
但每次都 `CallNextHookEx` 把按键原样放行，别的程序完全不受影响。

钩子回调里**只记录光标位置**，真正的生成放在主循环里做，避免在钩子里
做内存分配（低级钩子回调超时会被系统悄悄摘掉）。
要换键就改 `main.cpp` 里的 `SPAWN_KEY_VK`（默认 `VK_OEM_PERIOD`）。
