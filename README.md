# Fall_And_Boom

Windows 桌面小玩具：图片从屏幕顶端掉落，落到窗口顶边会停住并跟着窗口移动，
被快速拖动的窗口"创飞"，存活 5 秒后炸成碎片，爆炸还会把附近的图片一起炸飞。
被以特别快的速度撞击时，引信会缩短 2.5 秒。

图片分**两类**，各放一个文件夹：

| 文件夹 | 类别 | 行为 |
|---|---|---|
| `images\blocks` | **方块** | **不会自己爆炸**，也不闪；停稳一会儿淡淡消失。只有当爆炸物炸到它时才被炸成碎片 |
| `images\explosives` | **爆炸物** | 现有逻辑：掉下来 → 停住/被创飞 → 引信到点自己爆炸 → 冲击波炸飞周围 |

> 详见文末的「AI 生成声明」与 [LICENSE](LICENSE)。

## 特性

- Win32 + GDI+ 单窗口合成，整屏 layered window 一次提交
- 图片格式：`png` / `jpg` / `jpeg` / `bmp` / `gif` / `webp` / `tif` / `ico`
  - 优先用 GDI+ 解码；遇到 WebP、JPEG XL 等它不认识的格式自动回退到 WIC
  - 支持多帧 GIF 动画
- **方块 / 爆炸物两类图片**，各自有独立的尺寸、下落速度、生成权重、数量上限（见下方「方块与爆炸物」）
- 把其它程序的窗口顶边当作平台；**全屏 / 无边框全屏窗口会被忽略**
- **被其它窗口遮住的那段顶边不会被当成平台**，不会出现"悬空停住"
- 停住的图片会跟随窗口做**水平和垂直**移动（窗口往上拖也会被顶上去），
  而且**拖动多快都跟得上**（不再有 250 px/s 的速度上限）
- 被撞飞的图片会与**窗口侧面**正常碰撞推挤，不会穿模
- 把窗口往**上**拖时，压在它顶边上的图片会被一起顶上去，不会穿过窗口
- 顶边上面**放得下才站得住**：48px 的图片要顶边在 y ≥ 48，12px 的碎片 y ≥ 12 就够。
  顶边贴着屏幕上沿的窗口（含最大化、贴顶）就穿过去，不会被硬塞到屏幕顶端卡住
- **爆炸产生的碎片也会落在窗口顶边上**（和图片用同一套落点判定）
- **开始菜单 / 搜索 / 通知中心这类 shell 浮层也能碰撞**（见下方「z-band 窗口」）
- 顶边太低（贴着屏幕顶端，例如右侧贴满全高的通知中心）的窗口站不上去，
  但它**落在工作区里的那条侧边仍然是墙**，弹飞的图片会撞在上面
- 爆炸产生冲击波，把半径内的其它图片一起炸飞（被炸飞不变浅）
- 爆炸前 3 秒开始闪烁，0.6 秒一个周期
- **两个手动生成键**：一个只出方块（默认 `,`），一个只出爆炸物（默认 `.`），按键位置生成，不用等自动掉落
- **所有可调参数都在 exe 同目录的 `config.ini` 里，改完重启程序生效，不用重新编译**（见下方「配置」）
- 光标完全穿透，不抢焦点

## z-band 窗口（为什么开始菜单要单独处理）

Win11 的开始菜单、搜索、通知中心这类 shell 浮层是用 `CreateWindowInBand` 建在
**比默认 z-band 更高的 band** 上的。它们是货真价实的顶层窗口 ——
`WS_POPUP | WS_VISIBLE`、父窗口是桌面、没被 DWM cloaked、`GetWindowRect` 也正常 ——
但下面这些 API **一个都枚举不到它们**（实测确认）：

`EnumWindows` / `EnumChildWindows(GetDesktopWindow())` / `FindWindow` /
`GetWindow(GW_CHILD)` 链 / `EnumThreadWindows`

唯一能拿到的是 `GetForegroundWindow()`。所以 `ScanWindows()` 会先问一次前台窗口：
如果它**不在** `EnumWindows` 的结果里，就说明它是 band 窗口，于是把它插到
`g_windowList` 的最前面（它的 Z 序本来就在所有窗口之上）。这样它既能当平台，
又能作为遮挡源，让被它压住的其它窗口顶边正确地失去停靠点。

代价：一次扫描多一次 `EnumWindows` 探测（命中前台窗口就提前返回，通常几十次迭代）。
另外 band 窗口同一时刻只可能有前台那一个，但 shell 浮层本来也是互斥弹出的。

### 遮挡判定：只认"实心窗口"

"顶边被压住就不当平台"这条不能按 Z 序无条件算。

Win11 把窗口往屏幕上方拖时会弹**贴靠布局预览**，还有通知中心、输入法候选窗等，
这些壳层浮层都是**顶层合成层**（`WS_EX_NOREDIRECTIONBITMAP`，有时再加
`WS_EX_LAYERED`）。它们会浮在正在被拖动的窗口上方，一旦当成遮挡，被拖窗口的
**整条上缘就作废了** —— 现象就是"拖动时上缘接不住、也推不动，松开鼠标立刻恢复"
（浮层随拖动结束消失）。侧缘不走遮挡判定，所以侧缘一直正常。

两道闸：

- `BlocksAsOccluder()`：合成浮层 / 半透明层**不再算遮挡**（前台浮层除外，
  开始菜单这种要照旧压住后面的窗口）。真正的实心窗口（浏览器 / 编辑器 /
  资源管理器）不受影响，照旧遮挡。
- `TopEdgeVisibleAt()`：**用户正在操作的那个窗口（前台）的上缘永不作废** ——
  拖动过程中飘上来的任何东西都不该让它的顶边失效。

## 碰撞解算（为什么"上推"要单独处理）

### 1. 落点判定：`CrossesTopEdge()`

窗口矩形是每 `WINDOW_SCAN_SEC`（默认 0.09 秒）采样一次的，所以快速拖动时
**一帧能跳几十甚至上百像素**。这会让"最小穿透深度"这套判定选错轴：

- 窗口**往下**压或左右推时，图片相对窗口是"迎上去"的，最小穿透轴天然是对的轴；
- 窗口**往上**冲时，图片相对窗口在往下走，于是"从窗口底边穿出去"会先变成最小穿透轴
  —— 图片被从窗口下沿挤出来，看起来就是窗口从它身上穿了过去。

更麻烦的是，如果窗口一帧直接跳过了图片，两者**根本不再相交**，连重叠判定都不成立。

所以落点判定统一走 `CrossesTopEdge()`，它是两条判据取或：

**（a）图片掉下来 —— `SweptDownPastTop()`**：参照边取
`max(上一拍的顶边, 这一拍的顶边)`。

- 窗口静止 / 下移 → 参照边 == 当前顶边，判据和以前完全一样，行为不变；
- 窗口上移 → 参照边 == 上一拍的顶边，"原本在顶边之上、这一拍被吞进来"
  就能判出来，图片会被顶到新的顶边上。

**（b）窗口顶边升上来 —— `RisingTopLifts()`**：光有 (a) 还不够。

(a) 的前提是"图片底边上一拍还在顶边**之上**"。可图片经常是**停在屏幕底部
（或别的平台上）不动**的，窗口顶边从它下面升上来时，第一拍就可能已经越过它的底边
（窗口上一拍还在工作区外面 / 刚进列表，没有上一拍记录），之后 `prevBottom` 永远
大于参照顶边 —— 判据一直不成立，顶边直接从图片身上升过去。
表现出来就是**"接不住也推不动"：顶边扫过图片，图片纹丝不动**。

所以再按"扫掠"本身判一次：顶边这一拍扫过的竖直线段 `[这一拍顶边, 上一拍顶边]`
如果与图片身体 `[底边 - 高度, 底边]` **相交**，并且图片底边现在还在新顶边之下，
就把图片抬到新顶边上（并记下 `restingOn`，之后由第 4 节的跟随逻辑接管）。

- 顶边本来就远在图片上方的（图片整个在窗口肚子里）**不算** —— 那是一次瞬移，
  这正是以前"图片突然被吸到窗口顶上"的成因。

替换成一句话：**图片底边越过顶边**（图片掉上去）和**顶边越过图片身体**
（窗口顶边升上来），两种穿越都要认。

多个平台同时命中时由 `FindLandingTop()` 取**顶边最高**的那一个：正常下落时先碰到
的就是最高的那块；被上升窗口吞进来时，这也是唯一不留下穿模的解（落到更低的那块上
会和已经升上来的窗口重叠，下一帧再被抢一次，来回抽搐）。

图片、被弹飞的图片、爆炸碎片三条路径用的都是这套判定，所以碎片也会停在窗口顶边上，
而且会跟着窗口上下走。

### 2. 飞行的图片：按"上一拍在窗口哪一面"解算

被弹飞的图片（抛物线状态）走的是 `CollideWithWindows()`。

最早的版本按**最小穿透深度**选轴，它有坑：只看"离哪条边近"，不看图片是从哪进来的。
图片贴着窗口左/右边缘时 `pLeft`/`pRight` 比 `pTop` 小，就被甩到窗口侧面；
贴着底边时 `pBottom` 最小，被甩到下方 —— 视觉上就是
**"用窗口上缘推图片，图片瞬移到窗口下方/侧方，直接穿过窗口"**。

中途试过"从上方越过顶边进来的一律顶到顶边上面"这条优先级，结果引入了另一个
对称的毛病：一个被窗口**侧边**撞到、位置恰好在窗口**上半部分**的图片，
只要窗口这一拍也在往上走，就会被这条宽松的顶边判据捞走 ——
**侧边撞的却瞬移到窗口顶上**。

现在改成**先看上一拍在哪一面**，而不是看距离、也不看单轴的判据：

- 参照矩形取"这一拍和上一拍并起来"的那一层（窗口自己动过的那条边用上一拍的位置，
  否则快速拖动时判不出"上一拍还在外面"）；
- 四个面互斥：上一拍只可能在窗口外面的一侧，所以最多只有一个成立；
  **上一拍在窗口左边就从左边推回去，在上面就顶到上面**，不存在"侧撞按顶边解"；
- "从上面进来"额外要求**上一拍横向就已经和窗口重叠**（`inX`）——
  正是这一条挡掉了"侧撞瞬移到上方"；
- 四个面都不是（上一拍就已经在窗口肚子里）才退回最小穿透，并且带护栏：
  左/右/下三条边的穿透深度不超过一个身位，底边还要求图片相对窗口在往上走
  （否则一个往下穿过窗口的图片会在退出底边的瞬间被"啪"地按到 `wr.bottom` 上）。
  穿透超限的干脆不解析，让它按物理自己落出去 —— 总比瞬移到另一条边上强。

### 3. 顶边上面放不下就别硬塞（`TopEdgeFits()`）

"这条顶边能不能**接住**一张图片"是按**图片自己的高度**算的：`窗口顶边 y >= 精灵高度`。

- 48px 的图片需要顶边在 y ≥ 48 以上；
- 12px 的爆炸碎片只要顶边在 y ≥ 12 以上，所以碎片能停在图片停不了的矮窗口上。

顶边在屏幕上方（`top < 高度`）的窗口接不住，就**老老实实让图片穿过去**——
全屏、最大化窗口（顶边在 -7）也因此自动出局，不必再单独判。

> 曾经试过放宽成"顶边贴着屏幕上沿也算平台"，再把图片的 `y` 钳到 0。
> 结果是一场灾难：被拖到屏幕上沿的窗口（以及拖动时系统临时冒出来的全宽浮层）
> 全变成 y=0 的架子，**新生成的图片一出来就卡在屏幕最上方不下落**。
> 所以"接住"这条不能放宽：放不下就是放不下。

### 4. 已经在顶边上的图片：跟着窗口走，不设速度上限

"接住"严格，但**已经停在顶边上的图片**是另一套逻辑，它必须一直跟着窗口：

- **不要求 `TopEdgeFits`**。窗口被往上拖到顶边上面放不下时，图片压在 `y = 0`
  继续跟着走。放掉它才是错的 —— 用户看到的是"图片莫名其妙从窗口顶边上掉下去"。
- **水平跟随不设"游戏性"上限**。原来卡在 `FOLLOW_MAX_VX = 250 px/s`，
  而拖动窗口轻松就超过它，于是窗口直接从图片脚下被抽走 ——
  "图片跟不上 / 滑出去 / 然后掉下去"。图片本来就压在窗口顶边上，窗口一动它当然
  要跟着走。现在只留一个荒谬值上限（`FOLLOW_SANITY_VX`）挡窗口矩形抖动。
- **垂直位置在扫描点对齐、帧间按窗速外推**。窗口矩形每 0.09s 才采样一次，
  只写 `y = 顶边 - 高度` 的话图片每 0.09s 才动一下，看起来一顿一顿地"跟不上"。
  所以扫描那一帧精确对齐（`g_scanAccum == 0`），之后按 `顶边速度 × 已过去时间`
  平滑外推，下一次扫描再对齐回来。水平方向顶边上没有参照点，只能按窗速积分。

## 方块与爆炸物

图片放在 exe 同目录的 `images\` 下面，**分两个子文件夹**（只扫一层，不递归）：

```
images\
    blocks\        方块    —— 不会自己爆炸
    explosives\    爆炸物  —— 有引信，到点自己爆炸
```

`images\` 根目录里直接放的图片按**爆炸物**处理，兼容老版本。

两类的差别只有一条：**有没有引信**。

| | 方块 `blocks` | 爆炸物 `explosives` |
|---|---|---|
| 引信 / 自己爆炸 | ✗ 永远不炸 | ✓ `EXPLOSIVE_LIFE_SEC`（默认 5）秒后炸 |
| 临爆闪烁 | ✗ 不闪 | ✓ 最后 `EXPLODE_WARN_SEC` 秒开始闪 |
| 高速撞击扣引信 | ✗ | ✓ 相对速度 ≥ `FAST_HIT_SPEED` 时扣 `FAST_HIT_LIFE_LOSS` |
| 被爆炸波及时 | **炸成碎片**（`BLOCK_DESTROY_IN_BLAST`） | 被炸飞，引信不变 |
| 被炸掉之后 | 自己再放一次冲击波 → **连锁**（`BLOCK_CHAIN_EXPLOSION`） | 到点才炸 |
| 停稳之后 | `BLOCK_STAY_SEC`（默认 12）秒后**淡出消失**，不爆炸 | 到点爆炸 |
| 下落 / 尺寸 / 生成权重 | `BLOCK_*` 各自一套 | `EXPLOSIVE_*` 各自一套 |

### 方块为什么要"淡出消失"

方块没有引信，如果它落在屏幕上就永远不走，屏幕几十秒就会堆满，
而且 `MAX_FALLING` 上限会被这些"停着不动"的方块占满，**新图片再也生成不出来**。
所以方块停稳（不受重力、竖直速度归零）之后开始倒计时：
`BLOCK_STAY_SEC` 秒到点就淡出消失，**不是爆炸**，也不产生碎片。
一旦它被炸飞/被创飞又动起来，计时立即重置，不会在空中就淡没了。

`BLOCK_STAY_SEC = 0` 表示一直留着（那就要自己盯着 `MAX_FALLING` / `MAX_TOTAL`）。

### 爆炸是怎么传播的

1. 爆炸物引信到点 → 爆炸：放一次冲击波（`EXPLOSION_RADIUS` / `EXPLOSION_POWER_*`），
   自己炸成 `DEBRIS_COLS × DEBRIS_ROWS` 的碎片。
2. 同一次解算里，**中心落在爆炸范围内的方块**（按方块自己的中心点到爆心的距离算）
   全部被标记为炸掉，冒出方块碎片；`BLOCK_DESTROY_IN_BLAST = false` 时跳过这一步，
   方块只是被冲击波掀飞。
3. `BLOCK_CHAIN_EXPLOSION = true` 时，被炸掉的方块**自己再放一次冲击波**
   （用 `BLOCK_BLAST_*` 那一组，默认半径 150、威力更小），于是它范围内的方块继续被炸掉
   —— 这就是连锁。链式展开写成一个待处理清单，每个方块只会被炸一次，不会死循环。
   `false` 时方块照样炸成碎片，但不再向外传播。
4. 方块爆炸**不会**缩短别的爆炸物的引信，爆炸物只有"自己到点"和"被高速撞击"两条路。

> WebP 依赖系统安装的解码器（Win10/11 通常自带）。
> 若某张图片解不了，程序不会崩溃，只会在全部图片都失败时弹窗列出文件名。

## 配置（`config.ini`）

**所有可调参数都在 exe 同目录的 `config.ini` 里，改完重启程序生效，不用重新编译。**

文件不存在时程序会按内置默认值自动生成一份，里面每个参数都带中文说明；
**已有的文件永远不会被覆盖**（只会被读取）。文件按三段用 `# ---` 注释分开：

```ini
# ------------------------------------------------------------
# --- 通用 common
#     两边都适用的东西: 生成节奏、窗口扫描、碰撞反馈、按键
# ------------------------------------------------------------
DROPTIME_MIN = 0.2                # 两次自动生成的最小间隔, 秒(掉落快慢主要看这两个)
MANUAL_SPAWN_ENABLED = true       # 按下面两节里配的键手动生成 true / false

# ------------------------------------------------------------
# --- 方块 blocks  (images\blocks)
#     不会自己爆炸, 也不会闪; 只有被爆炸波及时才会炸成碎片
# ------------------------------------------------------------
BLOCK_SIZE = 48                   # 方块显示边长, 像素(会自动缩放)
BLOCK_SPAWN_KEY = ","             # 按这个键在鼠标位置生成一个方块
```

写法规则（都是为了让"写错一个字"不至于让程序罢工）：

- 只认 `键 = 值` 这一行；键名**忽略大小写、下划线、横线和空格**
  （`BLOCK_SIZE` / `block-size` / `block size` 等价）
- `#` 或 `;` 开头的整行是注释；行中间只有**前面是空白**才算注释
  （所以 `BLOCK_SPAWN_KEY = ";"` 这种值不会被误伤）
- `[小节标题]` 会被跳过，习惯怎么写都行
- **删掉某一行 = 该参数用内置默认值**
- 布尔值写 `true` / `false`（也认 `1/0`、`yes/no`、`on/off`、`开/关`）
- 数字支持 `0x` 十六进制
- 按键既可以写一个字符（`"."`、`"F"`、`"1"`，引号可省），也可以写虚拟键码数字
- 认不出的键、解析不了的值只影响**它自己**：启动时弹一次窗列出问题，其余照常生效
- 明显越界的值会被夹回可用范围（例如 `DROPTIME_MIN` 比 `DROPTIME_MAX` 大就自动交换），
  免得写错一个数就让程序崩掉或卡死

编码随便存（UTF-8 带不带 BOM、GBK 都能读）；改文件不用重启电脑，**重启程序**即可。

## 手动生成（两个键）

`config.ini` 里给两类图各配了一个键，按下就在**鼠标当前位置**生成一个：

| 键 | 默认 | 生成 |
|---|---|---|
| `BLOCK_SPAWN_KEY` | `,` | 一个方块 |
| `EXPLOSIVE_SPAWN_KEY` | `.` | 一个爆炸物 |

生成点以光标为中心，会夹进工作区，不会生成到屏幕外。
长按的自动重复会被 `SPAWN_KEY_DEBOUNCE_MS`（默认 250ms）挡掉，**两个键各自计时**
（先按逗号再按句号不会被互相挡掉）。

指定的那一类一张图都没有时（比如 `BLOCKS_ENABLED = false`，或者 `blocks` 文件夹是空的），
按键**退回生成另一类** —— 按下去一点反应都没有比"出了另一类"更让人困惑。
不想要某个键就把它设成另一个键一样的值（那样它永远轮不到）或干脆关掉
`MANUAL_SPAWN_ENABLED`。

键的写法：一个字符（`"."` `","` `"B"` `"1"`，引号可省）或虚拟键码数字（`0x70` 就是 F1）。
两个键写重了不会报错，钩子里**以 `BLOCK_SPAWN_KEY` 为准**，程序不会偷偷帮你改键。

自动生成和手动生成可以单独关掉（`config.ini` 里的 `AUTO_SPAWN_ENABLED` /
`MANUAL_SPAWN_ENABLED`）：

| `AUTO_SPAWN_ENABLED` | `MANUAL_SPAWN_ENABLED` | 效果 |
|---|---|---|
| `true` | `true` | 默认：自动随机下落，随时可以按 `,` / `.` 各补一张 |
| `false` | `true` | 屏幕一直干干净净，**只有按键才会出现图片** |
| `true` | `false` | 只能等自动随机下落，连键盘钩子都不会装 |
| `false` | `false` | 什么都不会生成（退出热键仍然有效） |

关掉 `MANUAL_SPAWN_ENABLED` 时连 `WH_KEYBOARD_LL` 钩子都不装，
不会白白往系统里挂一个全局键盘钩子。

实现上不能用 `RegisterHotKey`：那会把这个键从**所有程序**手里抢走，
打字、输入符号就全废了。也不能靠 `WM_KEYDOWN` —— overlay 窗口带
`WS_EX_NOACTIVATE | WS_EX_TRANSPARENT`，永远拿不到焦点。
所以这里装的是 `WH_KEYBOARD_LL` 低级键盘钩子：全局看得见，
但每次都 `CallNextHookEx` 把按键原样放行，别的程序完全不受影响。

钩子回调里**只记录光标位置和类别**，真正的生成放在主循环里做，避免在钩子里
做内存分配（低级钩子回调超时会被系统悄悄摘掉）。
换键就改 `config.ini` 里的 `BLOCK_SPAWN_KEY` / `EXPLOSIVE_SPAWN_KEY`。
